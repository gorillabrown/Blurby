WHAT I OBSERVED IN THE CODE (main = b4335606):
- Provenance is declared before generation, not recorded from the result. kokoroStrategy.ts:368 passes timingTruth "word-native" into the cache identity, and ttsCacheIdentity.ts:52 defaults it the same way. generationPipeline.ts:523-525 copies the identity's label onto every chunk. The `result.wordTimestamps ? ...` branch is never reached for Kokoro, because an identity always exists.
- onChunkReady always runs segmentKokoroChunk (kokoroStrategy.ts:423-432). When the table is missing or mismatched (hasUsableWordTimestamps, segmentKokoroChunk.ts:154-168), buildFallbackTimeline spreads the voiced duration by computeWordWeights (:170-189). createSegment then emits that estimate as `wordTimestamps` (:106-112, :131) with the parent's label (:126). Nothing records that the table was estimated.
- The scheduler's check is structure-only. A pass sets isTrustedWordTiming:true and timingTruth `chunk.timingTruth ?? "word-native"` (audioScheduler.ts:478-491). The "kokoro-duration-tensor" telemetry string is DEV-only (:495-508). In production the mislabel is the trust flag and the label, not that string.
- Both verifiers corrected the auditor on two points: the reach is understated, and the label comes from the cache identity, not the scheduler. I agree with both.

WHAT I EXECUTED (read-only; the model was copied to scratch work\F2-remedy first):
- The installed model_q4.onnx (sha256 prefix 04cf570cf9c41536) loaded in onnxruntime-node reports outputNames ["waveform"] only. A byte search found 0 occurrences of "durations". The patch reads `{waveform, durations:_dur}` from the model output (patches/kokoro-js+1.2.1.patch), so _dur is always undefined and the worker returns `wordTimestamps: null` (main/tts-worker.js:163).
- Inferred from that: on this install, every Kokoro chunk the owner heard ran on a weighted estimate labelled trusted and "word-native". The fallback was the only path, not an edge case.

This matches main/tts-cache.js: line 130 puts the declared label into the content key, and lines 217-249 compute trust from that declared label plus structure.
- So section F's "Opus/cache: preserve old cache without trusting it" row holds for provenance: the old cache has nothing trustworthy to offer. # F7-persist — accept_with_narrowing

**Rationale:** The finding holds. I confirmed it by reading the source at b4335606. I did not re-run the verifiers' executions; both had already executed the verbatim lines with deferred and rejecting fake filesystems.

What I observed in the source:
- main.js:130 is `function saveSettingsFn() { writeJSON(getSettingsPath(), settings); }` with no return, so the promise of the async writer at main.js:55-60 is thrown away.
- `await saveSettingsFn();` at main.js:293 therefore waits for nothing. A failed write never reaches loadState; it only shows up as an unhandled rejection.
- The removal spec presents a save call as completed persistence: ROADMAP.md:240 ("That is the persisted value"), 241 ("persists \"flow\""), 460 ("which persists the normalized result") and 476 ("This persists the normalized value"). Line 251's wiring grep checks for the no-op `await` by its text.

Why I narrow it instead of adopting the auditor's option A:
1. **The removal's invariant does not depend on the write completing.**
   - The only reader of the local settings.json is loadState (main.js:290; git grep of getSettingsPath finds only main.js:41, 130, 290 and 291).
   - The spec's loadSettingsData normalizes on every load (ROADMAP.md:468), and each cloud apply normalizes before it saves (ROADMAP.md:473).
   - So a lost or failed write cannot bring "narrate" back into memory.
   - writeJSON serializes synchronously at the call (main.js:58, inside the async body before the first await). The structuredClone sink in Done-when 7(b) is therefore an exact model of the bytes a successful write lands. Only completion and failure are unproven, not content.
2. **Option A is not the one-line change the report implies.**
   - With `return writeJSON(...)`, a rejected startup write (an EPERM, EBUSY or ENOENT rename on Windows) would reject loadState inside `app.whenReady().then(async ...)` (main.js:611-731), which has no .catch. Startup would stop before window creation.
   - Awaiting the save in applyCloudSettings would let a settings write failure abort startSync's library and history sync (sync-engine.js:813-816).
   - Both effects would be new behaviour in a sprint that already runs alone over the shared-core freeze set.

So the removal spec takes option B:
- reword "persists" to "submits to the settings save";
- add an explicit durability boundary to D12;
- qualify D13's "stay flow";
- add one check that the writer contract is unchanged, so an implementation agent cannot "fix" the no-op await without a failure policy.

The pre-existing writer gap is real but older than the removal and not caused by it:
- every settings save is fire-and-forget;
- settings.json.tmp is shared between overlapping writes, which raised ENOENT and, under 8-way overlap, left a stale snapshot in both verifiers' Node controls on real NTFS (not reproduced under Electron);
- saveHistory and saveSiteCookies (main.js:153-154) follow the same pattern;
- will-quit (main.js:737-754) flushes only the library, so a save-settings IPC write still inside its 500 ms debounce (main/ipc/state.js:29-31) can be lost at quit.

That gap goes to a new Low Platform & Maintenance bug, BUG-185 (next free number; git grep finds no BUG-185 or later). Severity: Medium as spec accuracy, Low as runtime risk to the removal. It does not block dispatch once the wording is corrected.
