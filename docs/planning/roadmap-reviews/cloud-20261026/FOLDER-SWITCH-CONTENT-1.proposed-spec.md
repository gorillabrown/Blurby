## 3. Main owner and FIFO linearization
One main-process queue instance is created before state IPC registration and shared by BOTH legacy and new handlers. It is not created inside register(), a window or renderer. All senders/remounts use the same authority.
At synchronous IPC admission allocate distinct main requestId and admission sequence, append once, publish pending metadata; malformed transport payload gets a typed precommit failure without effect. Even a valid request for the same folder/path is a distinct queue item. No deduplication by path or client ID. clientRequestId is correlation only, not an authorization token or globally trusted sequence.
The queue owns work from dialog open/access validation to immutable response construction. Use a recovered tail internally (item completion success OR failure advances it); callers still receive their own actual outcome. It must not wait for a renderer to receive/acknowledge a response. No swallowed rejected promise or globally pending lock.
select-folder dialog occurs only at its FIFO turn; canceled dialog never changes sourceFolder/recentFolders, resets notice or starts watcher. switch-folder evaluates recent-folder trust and access AT its turn, retaining exact original trust/permission policy; validation is not done concurrently outside the queue. C canceled/refused after B completed leaves B. C committed then failing leaves actual C unless a separately authorized main operation subsequently commits something else.
COMMIT is one synchronous non-awaiting main critical section after dialog/validation: capture old origin; advance epoch; assign sourceFolder and bounded recentFolders; invalidate prior folder-origin operations; update current ownership record; retain the entire library; capture commit publication. Same-path accepted commit advances epoch and replaces ownership. No event/reentrant callback inside this section may observe new folder with old epoch or vice versa.
After commit, request/observe settings persistence, start new watcher before new sync, await actual sync outcome, then construct immutable settlement while still holding its FIFO turn. No early IPC return to make loading appear faster. Existing sync cancellation wait/list/stat/save intervals unchanged.
Linearization separates committed in-memory selection from durable save, watcher health and sync completion. There is no atomic filesystem transaction across those effects, and no renderer rollback.
Stage tracking per request: dialog/validation -> commit -> settings-save -> watcher-start -> sync -> snapshot. Each stage captures completed/failed/not-attempted accurately. A settings-save error is recorded; continue existing watcher/sync path where safe rather than implicitly rolling back or skipping all later stages. A synchronous watcher throw is contained so actual sync still gets a recorded attempt; missing watcher handle is a degraded watcher outcome with existing notice, not fake success. Brain review must verify this preserves existing intended workflow.
syncAll currently logs/catches failures and returns void; a new caller cannot infer success from resolved Promise<void>. Add internal structured run outcome (done, canceled, root-unlistable, root-empty-suspect, partial-read, sync-failed, stopped) without changing legacy return projections. Preserve swallowed-error safety for fire-and-forget callers while exposing the real outcome to transition settlement.
Finish the item by removing it from active/pending metadata and capturing a final snapshot BEFORE starting the next queue item. If snapshot construction itself fails, do not clear renderer pending via an invented success. Record error, settle request as failed without a fabricated snapshot, recover queue tail and permit later items. A later authoritative getter can reconcile actual state; it cannot pretend to have recovered the lost request outcome.
A sender destroyed after admission does not cancel accepted main work. Queue continues and main broadcasts coherent state. Onboarding's legacy select-folder enters the same FIFO; no onboarding source change is necessary for serialization.

### Exact response semantics
Precommit canceled/refused: committed=false, commitEpoch=null, source remains actual prior main state; final snapshot still reflects any independent legitimate library changes.
Postcommit failure: committed=true, commitEpoch set to actual epoch, status=failed, real stage failures/sync outcome and actual selected folder in final snapshot. Never map rejected IPC to no-commit.
Outcome mapping is exact: status=completed only when settings save succeeded, watcher started and sync is done or partial-read; partial-read keeps existing skipped-path retention/warning and is not a claim all files imported. Any postcommit stage failure, unreachable/empty-suspect/stopped/canceled/sync-failed outcome is status=failed with committed=true. Precommit user dialog cancel alone is status=canceled; validation refusal is status=refused.
Successful accepted same-folder request: committed=true, new requestId and epoch, actual watcher/sync completion, status=completed.
An existing Cancel Sync action is not Cancel Folder Selection. Preserve its run cancellation semantics; settlement reports canceled sync, actual committed source and retained records. Do not invent a rollback or cancel a later queue item.
Legacy select-folder returns folder/null using the same coordinator outcome projection; legacy switch-folder retains {folder}/{error}. Preserve precommit messages. Postcommit operational failures must remain distinguishable in NEW response; do not infer them from legacy projection. If preserving old legacy postcommit result behavior conflicts with failure visibility, return to Brain rather than changing old callers silently.

## 4. Exact additive transport and schema (proposed names for review)
Keep legacy getState(), selectFolder(), switchFolder(folder), onLibraryUpdated(array) and channels get-state/select-folder/switch-folder/library-updated unchanged in payload shape. get-state continues pickUserSettings(settings) plus sourceFolder/recentFolders and !deleted library, now deep cloned at one synchronous capture point.
Add these methods to preload and ElectronAPI in src/types.ts:
- getLibrarySnapshot(): Promise<LibrarySnapshotV1> -> invoke("get-library-snapshot").
- selectFolderTransition(clientRequestId: string): Promise<FolderTransitionResultV1> -> invoke("select-folder-transition", {clientRequestId}).
- switchFolderTransition(folder: string, clientRequestId: string): Promise<FolderTransitionResultV1> -> invoke("switch-folder-transition", {folder,clientRequestId}).
- onLibrarySnapshot(callback: (snapshot: LibrarySnapshotV1) => void): () => void -> listen/removeListener("library-snapshot").
Validate only expected fields/types; never accept a requested epoch/revision/session or filesystem trust grant from renderer.

LibrarySnapshotV1:
{
 protocolVersion:1,
 mainSessionId:string,
 epoch:number,
 revision:number,
 settings:BlurbySettings,
 library:BlurbyDoc[],
 folderWork:{
  active:{requestId:string, clientRequestId:string|null, kind:"select"|"switch", stage:"dialog"|"validation"|"commit"|"settings-save"|"watcher-start"|"sync"|"snapshot", commitEpoch:number|null}|null,
  pendingCount:number,
  lastSettledRequestId:string|null
 }
}
All numbers are nonnegative safe integers; epoch/revision counters stop publication with a real error on overflow, never wrap. mainSessionId is opaque per-main-process random UUID, generated once; epoch starts0 after loadState establishes initial source, revision starts0 then increments for EACH captured publication/getter/settlement. Neither is a cloud/device sync revision, persisted setting, timestamp, path or renderer generation. Distinct capture => distinct revision even if bytes equal. No revision is allocated for a snapshot that fails cloning.
No requested folder path from a queued dialog is disclosed or invented; settings describes actual committed main state, optimistic target stays renderer-local. pendingCount excludes active. Last-settled ID is correlation metadata, not a claim every earlier request succeeded.

FolderTransitionResultV1:
{
 protocolVersion:1, mainSessionId:string, requestId:string,
 clientRequestId:string|null, kind:"select"|"switch",
 status:"completed"|"refused"|"canceled"|"failed",
 committed:boolean, commitEpoch:number|null,
 stages:{settingsSave:"not-attempted"|"saved"|"failed",
         watcher:"not-attempted"|"started"|"failed",
         sync:"not-attempted"|"done"|"canceled"|"root-unlistable"|"root-empty-suspect"|"partial-read"|"sync-failed"|"stopped"},
 error:{stage:string, message:string}|null,
 snapshot:LibrarySnapshotV1|null
}
status=canceled describes dialog precommit cancellation; run cancellation is status=failed with stages.sync=canceled, committed=true, so it cannot imply precommit cancel. If multiple failures occur preserve them in a content-free log keyed by requestId; primary error is earliest failing stage. error.stage/message must be sanitized existing user-safe strings, no stacks/settings secrets. Result and snapshot share mainSessionId; snapshot.epoch === commitEpoch at capture for committed requests and snapshot.folderWork.lastSettledRequestId=requestId at capture. Within FIFO settlement no later folder commit has occurred yet; independent library mutations can advance revision. snapshot=null is explicit unreconciled failure. No fabricated snapshot on IPC/serialization rejection.

main/library-publication.js owns captureLibrarySnapshot(), getFolderOrigin(), isCurrentFolderOrigin(), advanceFolderCommit(), publishLibrarySnapshot(). Dependencies read real sanitized settings and current live library. Capture synchronously deep-clones both settings and !deleted docs and folderWork, then freezes owned data for internal tests. No retained live nested doc references. No await or callback during clone. Date/undefined behavior must preserve existing structured-clone bridge types; do not JSON-stringify away fields or leak secrets. Legacy array event is a cloned array projection from the SAME captured snapshot; legacy get-state projection likewise. New consumers cannot use raw legacy and versioned events as two authorities.
main.js _doBroadcastLibrary captures at SEND time, not when its200ms debounce was armed. Send library-snapshot and legacy library-updated projections from that capture; preserve current destination policy (mainWindow only), not a new all-window architecture. Coordinator lifecycle/commit/settlement publishes immediate versioned snapshot through the same authority; legacy library event need only accompany normal library publication, not every queue metadata update.
No requirement to deep-copy all120k records on every in-memory field assignment: publication revision is assigned at actual capture, NOT a mutation counter. Synchronous batches are coherent and later snapshots reflect current state. In-place writes need producer validation but cannot mutate already captured snapshots. Measuring capture overhead is separate; do not sacrifice correctness by aliasing.

### Renderer session/bootstrap and barrier
Mount registers onLibrarySnapshot BEFORE invoking getLibrarySnapshot. Buffer validated events until getter resolves; getter response establishes mainSessionId for this mount. Choose highest revision of that same session among getter/buffer; then accept only strictly increasing revision and nondecreasing epoch. Same revision with differing bytes is a protocol error; equal duplicate is inert. A different-session event is not comparable and triggers unreconciled existing error handling plus explicit getter/bootstrap, not silent reset or an automatically repeated retry loop. Ignore old session afterward. In actual Electron main restart normally recreates renderer; tests still cover stale old-session transport.
Each folder invocation sets local monotonically increasing intent and unique clientRequestId synchronously; no renderer FIFO controls main ordering. Recent-folder source header/recent list are a presentation overlay over authoritative settings, not mutation of authoritative snapshot. Newest local pending intent owns the overlay; Browse invents no folder until committed.
Maintain authoritative snapshot separately from presentation intent/outstanding request promises. While pending/unreconciled or snapshot.folderWork active/pendingCount>0, card region remains excluded. New snapshots may update hidden retained data but do not end a still-unsettled own request. Older request result may be recorded but cannot remove newer local intent or error state.
A current result clears its own intent ONLY after a valid matching-session final snapshot and authoritative revision barrier are accepted. If a newer snapshot has already arrived, use it instead of replacing with the older result snapshot; require snapshot revision >= settlement revision and epoch >= commitEpoch. pending local successor/global active work keeps cards hidden. A stale result cannot supply a raw library fallback.
When status=failed after commit or snapshot missing, remain unreconciled using existing toast/log surface; do not present old cards as new. A valid authoritative refresh resolves UNKNOWN transport state only when no own request outcome is still unknown AND main reports no active/pending work; it must not certify failed sync as completed. Preserve existing FolderNotice banner for root/watch problems; no new Retry design. Brain/independent review must distinguish partial-read (existing keep/prune policy and warning) from unreachable/failed/canceled runs; no claim that coherent snapshot means full import success.
All hook getState refreshes (mount, CRUD catches, drop success) migrate to one getLibrarySnapshot acceptance function; version guard applies even outside folder operations. Other hook promises never call setLibrary from an unversioned getState result.

## 7. Consumer migration and presentation
