**HOTFIX-EINK-HOVER-1 investigation (Cowork-side, so CLI only executes):** `themes.css:145` `[data-eink="true"] *:hover { background-color: inherit; }` matches the hovered element **and every ancestor** (CSS `:hover` propagates up the tree). So any panel, dialog or backdrop containing the pointer takes its parent's background, which is usually transparent. BUG-184 saw this on Settings (`.menu-flap`). By the same mechanism it also hits the command palette, the import/bug-report/metadata/cloud-merge dialogs, the highlight menu, the definition popup and the overlay backdrops. The BUG report's `.menu-flap`-only fix would leave all of those broken. The spec instead scopes the rule to the elements that actually carry a hover-background rule (enumerated by grep). That keeps today's "no hover tint" behavior for controls and stops it reaching containers.

*Verified in headless Chromium (Playwright 1.56, minimal repro of a fixed `.menu-flap` with a hover-tinted button inside):* with the wildcard, the flap computes `rgba(0,0,0,0)` while a child is hovered. With the scoped rule, the flap keeps `rgb(1,2,3)` and the hovered button's own `:hover` tint is still suppressed (it inherits the now-opaque panel color).
